# Nextcloud app for Dwasm — implementation spec

## What

Package Dwasm — Gregory Maynard-Hoare's WebAssembly port of PrBoom+ / PrBoomX —
as a Nextcloud app, so a logged-in user can play modded Doom in the browser
inside Nextcloud, with no external server. Single player, Boom/MBF-class
compatibility (PWADs, UMAPINFO, DeHackEd/BEX), optional widescreen/uncapped-FPS
PrBoomX niceties. Freedoom is the default, and the user can import their own
IWAD, PWADs and patches.

This is the *packaging* path: the browser port already exists and is
maintained, so the work is a Nextcloud wrapper plus a launcher that feeds WAD
bytes into the engine. It is not dsda-doom: there is no MBF21, no UDMF and no
DSDA-format demo tooling (see Decisions). The dsda port is a separate, larger
project (`dsda-doom/docs/nextcloud-app/spec.md`), and the vanilla port is a
third option (`webdoom/docs/nextcloud-app/spec.md`).

## Context

### The repository

Dwasm is a fork chain: `Dwasm → PrBoomX (JadingTsunami) → PrBoom+`. It builds
natively and for WebAssembly from the same tree. Key facts:

- **The browser port is real and clean.** 131 `__EMSCRIPTEN__` guards, but the
  hot spots are well factored. The game loop is refactored into
  `D_LoopLoopIter` and driven by `emscripten_set_main_loop` (`src/d_main.c:569,
  647-655`); the native `for(;;)` is kept. `src/WASM/wasm_io.c` is the browser
  shim: it mounts **IDBFS** at `/dwasm` for saves/config, syncs with
  `FS.syncfs`, and calls back into JS via `Module.hideConsole`,
  `Module.showConsole`, `Module.winResized`, `Module.captureMouse`,
  `Module.softExit`.
- **Build:** `emcmake cmake .. -DCMAKE_BUILD_TYPE=Release` (optionally with
  `-DGL4ES_PATH=...`), producing `index.html`, `index.js`, `index.data`,
  `index.wasm`. `-DSINGLE_HTML_FILE=1` produces one self-contained HTML file.
  SDL2 and SDL2_mixer are used through Emscripten (`-sUSE_SDL=2`,
  `-sUSE_SDL_MIXER=2`). Music defaults to a self-contained OPL2 synthesiser
  (no SoundFont needed); Timidity is an optional build.
- **The internal WAD is mandatory.** `prboomx.wad` (459 KiB, SHA-256 pinned in
  `README.md`) must be generated by a native build and placed in `wasm/fs/`
  before the wasm build.
- **Content is build-time by default.** The repo's own `wasm/shell.html` (197
  lines) is minimal: spinner, canvas, console, pointer lock. WADs placed in
  `wasm/fs/` are preloaded into `index.data` with `--preload-file`. **There is
  no runtime WAD upload in the repository.**
- **Licence:** GPL-2.0 (`COPYING`); source headers say "version 2 … or any
  later version". The app licence decision depends on which reading holds (see
  D7).
- **Maintenance:** 37 commits from 2024-12 to 2026-04, 3 open issues, no tagged
  releases. The online deployment is the de facto release. It is low-velocity
  but alive, and it tracks upstream PrBoomX/PrBoom+ sporadically.

### What the hosted site actually is — and what you would download

The live app at **https://dwasm.m-h.org.uk/** is *not* the repository's minimal
shell. It is a richer, **closed** launcher (the files are served but are not in
the repo, and are not separately licensed as far as we can tell). It is the
working model for the launcher a Nextcloud app must provide, so its anatomy
matters.

The page runs a `Module` object, writes user-selected files into the Emscripten
memory filesystem, and sets `Module.arguments` to `-iwad`, `-file` and `-deh`
before loading `index.js`. Built-in games are downloaded and unpacked in the
browser by `getgame.js` + `libarchive.js`, then handed to the page as a
`{filename: [type, Uint8Array]}` dictionary (`type` = `i`/`p`/`d`) that
`Module.onRuntimeInitialized` writes into MemFS. Users can instead pick their
own IWAD and multiple PWAD/DEH/BEX files; there is an age-confirmation
checkbox, optional touch controls (`oly.js`), URL query args, and
localStorage for the last game choice.

Assets served by the page (all reachable today; sizes are as measured):

**Page-relative on `https://dwasm.m-h.org.uk/`**

| file | size | role |
|---|---|---|
| `index.html` | ~16.7 KB | launcher UI + inline `Module` config |
| `index.js` | 49,333 B | Emscripten glue |
| `index.wasm` | 930,872 B | the engine |
| `index.data` | 285,463 B | preloaded FS (`prboomx.wad` + defaults) |
| `libarchive.js` | 3,337 B | in-browser archive extraction loader |
| `libarchive.wasm` | 487,646 B | libarchive, for zip/LHA extraction |
| `freedoom1.bin` | 7,136,555 B | Freedoom Phase 1 IWAD (archive) |
| `freedoom2.bin` | 7,821,356 B | Freedoom Phase 2 IWAD (archive) |
| `getgame.js` | 1,447 B | downloader + extractor for built-in games |
| `oly.js` | 1,672 B | on-screen touch controls |

Note `libarchive.worker.js` is absent (404): the deployed `libarchive.js` is the
non-worker variant.

**Remote on `https://gmh-code.github.io/dwasm/`** (the `DLURL` baked into
`getgame.js`)

| file | size | built-in game | notes |
|---|---|---|---|
| `doom19s.zip` | 2,450,688 B | shareware | `DOOMS_19.1` + `DOOMS_19.2` joined, then LHA-extracted → `DOOM1.WAD` |
| `hacx12.zip` | 7,731,658 B | HACX | `HACX.WAD` |
| `harmonyc.zip` | 7,874,392 B | Harmony | `HarmonyC.wad` + `Harmony-WS.wad`, needs Freedoom 2 |
| `REKKR_1_17_4.zip` | 14,986,358 B | REKKR | `REKKR.wad`, needs Freedoom 1 |

`getgame.js` maps game ids to fetchers: `freedoom1`/`freedoom2` (page-relative
`.bin`), `sw` (shareware), `hx` (HACX), `hy` (Harmony), `rr` (REKKR). The last
three depend on a Freedoom IWAD being present.

**What this means for the port:** the hosted launcher already implements
everything a Nextcloud app wants — built-in free games, user WAD/PWAD/DEH
upload, MemFS writes, launch-arg assembly, and (via the repo's `wasm_io.c`)
IDBFS persistence. But none of it is in the repository, so it must be
reproduced, not vendored. Reproducing it is the bulk of this project.

### What we learned from the other apps

- `doom_nextcloud` and the webdoom spec define the Nextcloud wrapper: a
  `PageController` with the wasm CSP, an assets controller that serves
  `application/wasm` with an explicit `Content-Type`, subpath-safe URLs, no
  service worker, build artifacts in the release archive. Reuse it; do not
  redesign it.
- The dsda spec's engine analysis is the contrast: Dwasm keeps Boom/MBF and
  PrBoomX quality-of-life and runs today, at the cost of MBF21/UDMF/DSDA demos.

## Requirements

- **R1.** A logged-in user can open **Doom (Dwasm)** from the Nextcloud app
  menu and reach a playable game with no external server and no install.
- **R2.** Freedoom is available and selected by default, so first run works
  with no user action.
- **R3.** A user can import their own IWAD and one or more PWAD/DEH/BEX files,
  and the engine is launched with the correct `-iwad`/`-file`/`-deh` arguments.
- **R4.** Savegames and config persist across reloads and page navigations.
- **R5.** The engine runs in software mode by default; GL is optional and not
  required (frame-rate and texture-corruption caveats are documented upstream).
- **R6.** The app installs and runs under a Nextcloud subdirectory; assets are
  served with correct MIME types and a compatible CSP.
- **R7.** No third-party commercial game data is redistributed by the app
  without a verified licence; the licence of every downloaded/bundled asset is
  recorded.
- **R8.** The native build of the same tree still builds, so the fork stays
  mergeable (the port is additive).
- **R9.** The build is reproducible from a pinned upstream commit and a pinned
  Emscripten version.

## Design

### Engine: use the repository build, not the hosted bundle

Build from the repo. The hosted `index.*` are unpinned, unversioned and not
part of the GPL source release; the Nextcloud app should serve its own build
from a pinned commit. The hosted site is the behavioural reference, not a
dependency.

Two build shapes are possible:

- **Separate files** (`index.js`, `index.wasm`, `index.data`) — preferred, so
  the wasm and data can be cached and served with the right MIME types.
- **`-DSINGLE_HTML_FILE=1`** — one file, simplest to serve, but it embeds the
  preloaded FS and cannot host per-user content without a runtime write path
  anyway. Not preferred.

Build steps: native build to produce `prboomx.wad` (pinned SHA-256), place it
in `wasm/fs/`, then `emcmake cmake … && make`. Emscripten version must be
pinned in CI.

### Launcher: reproduce the documented `Module` contract

The Nextcloud front-end must do what the hosted page does. The interface it
uses is stable and small:

| hook | purpose |
|---|---|
| `Module.onRuntimeInitialized` | called after the FS exists; write user files here |
| `FS.open('/name','w')`, `FS.write`, `FS.close` | put IWAD/PWAD/DEH bytes into MemFS |
| `Module.arguments` | engine argv: `-iwad <f>`, `-file <f…>`, `-deh <f…>` |
| `Module.setStatus(text)` | loading/progress text |
| `Module.hideConsole()` / `Module.showConsole()` | switch between canvas and log |
| `Module.captureMouse()` / `Module.winResized()` | pointer lock and resize |
| `Module.softExit(code)` | exit path; IDBFS flush already handled in `wasm_io.c` |

The repo's `src/WASM/wasm_io.c` provides the IDBFS half unchanged, so
persistence (R4) is essentially free.

The launcher must also assemble the stack in the order the engine expects
(IWAD first, then PWADs in selection order, then DEHs) and reject a missing or
invalid IWAD with a message rather than a blank canvas.

### Content: what to bundle, what to download

Keep the Nextcloud app's own archive small and legal. Separately:

- **Bundle Freedoom Phase 1 and Phase 2.** Freedoom is freely redistributable;
  this gives R2 and a legal default. (Could be served as the same `.bin`
  archives the hosted site uses, or as plain `.wad` cross-compressed in the
  app tarball.)
- **Do not bundle** the shareware zip or the third-party mods. Reference the
  hosted downloads by URL instead of redistributing them, so their licences
  remain the upstream host's responsibility. The shareware episode is
  redistributable, but HACX, Harmony and REKKR need their own licences checked
  before this app ships any of their bytes.
- If the app is to mirror rather than link, verify each licence first
  (Freedoom: free/BSD-style; shareware: id's redistributable shareware;
  HACX/Harmony/REKKR: unverified here).

If the download path is kept, the page needs `connect-src` for the download
origins and `libarchive.js`/`libarchive.wasm` for zip/LHA extraction. An
alternative that removes both the external dependency and the libarchive
requirement is to support only plain `.wad` imports plus bundled Freedoom, and
drop the shareware/HACX/Harmony/REKKR downloaders for phase 1. That is the
recommended phase-1 shape: it is smaller, fully offline, and sidesteps the
content-licence question.

### Persistence

IDBFS is per-browser, exactly as in the webdoom spec's phase-1 decision. Phase
2 can move the user's WAD/save library to their Nextcloud files. `wasm_io.c`
already handles the mount and the flush-on-exit, so phase 1 needs nothing here.

### Nextcloud packaging

Identical to the webdoom spec's Design section; the only deltas:

- The payload is `index.js` + `index.wasm` + `index.data` (plus any bundled
  Freedoom), not a client module graph. Serve each with the right type;
  `application/wasm` for `.wasm` (the `doom_nextcloud` `getEmulatorFile`
  pattern), `application/octet-stream` for `.data`.
- If `wasm/fs` preloading is used, `index.data` carries the internal WAD and
  any bundled content; keep it below a sane size and do not put commercial
  content in it.
- CSP: `allowEvalWasm()` (`wasm-unsafe-eval`) plus `worker-src blob:` if
  libarchive's worker is used. Check whether the generated `index.js` needs
  `'unsafe-eval'` (Emscripten `DYNAMIC_EXECUTION` defaults); if so, rebuild with
  `-sDYNAMIC_EXECUTION=0` rather than widening the CSP. The hosted page uses
  `EMULATE_FUNCTION_POINTER_CASTS`-style paths and is not a CSP reference.
- Pinned-commit build in CI, artifacts in the release archive (the repo's
  `.git` ignores build output, as with the other two apps).

## Decisions

| # | choice | alternatives | why | reversible |
|---|---|---|---|---|
| D1 | Build the app from the Dwasm repo at a pinned commit | serve the hosted `index.*` | hosted files are unpinned, unversioned and not obviously licensed for redistribution; a pinned build is reproducible | yes |
| D2 | Write our own launcher against the documented `Module`/`FS` contract | vendor the hosted `index.html`/`getgame.js`/`oly.js` | those are not in the repo and have no clear licence; the contract is small and stable | yes |
| D3 | Phase 1: bundle Freedoom, support `.wad` import, no remote downloads | reproduce the hosted in-browser downloaders | smallest legal surface, fully offline; remote mods need licence review | yes |
| D4 | Software renderer by default; GL optional | GL4ES by default | upstream documents GL frame-rate variance and floor-texture corruption; software is the safe default | yes |
| D5 | Keep IDBFS persistence for saves/config | Nextcloud-files storage | already implemented and proven in `wasm_io.c`; per-user storage is phase 2 | yes |
| D6 | Separate `index.*` files, not single-file HTML | `-DSINGLE_HTML_FILE=1` | correct MIME types and caching; per-user content needs a runtime write path regardless | yes |
| D7 | Choose the app licence after confirming GPL-2.0-only vs -or-later | copy the AGPL choice from `doom_nextcloud` | `COPYING` is GPLv2 and headers say "or later"; if it is only, AGPLv3 is incompatible and the app must be GPL-2.0-or-later | no, once published |
| D8 | Treat the engine as Boom/MBF-class and say so in the store listing | imply dsda parity | it has no MBF21/UDMF/DSDA demos; users must not be misled | yes |
| D9 | Keep `__EMSCRIPTEN__` changes additive; native build stays green | fork the wasm build away from native | preserves mergeability with PrBoomX/PrBoom+ | yes |

## Versions

- **Dwasm:** pinned commit (currently `ddf0347`, 2026-04-14, "Add single file
  build capability"). Record it in the app repo.
- **Emscripten:** pin an emsdk version; the hosted site's toolchain is
  unknown, so do not treat it as a reference build.
- **PrBoomX / PrBoom+:** whatever the pinned Dwasm commit vendors.
- **Nextcloud / PHP:** the range used by the webdoom app spec (30–34, matching
  `doom_nextcloud`); confirm at release.
- **Freedoom:** current release; check `COPYING` and record the version.
- **libarchive / libarchive.js:** only if the remote-download path is kept;
  libarchive is BSD and libarchive.js is MIT — verify the bundled copy.

## Invariants

- **I1.** The native build still compiles from the same tree as the wasm build
  (R8); `__EMSCRIPTEN__` guards are additive.
- **I2.** Only verified-licence content is bundled (R7): Freedoom and
  `prboomx.wad` in phase 1.
- **I3.** The served `index.wasm` is the one the served `index.js` was linked
  with (do not mix artifacts across builds).
- **I4.** All client URLs are app-relative; the hosted site's `DLURL` /
  root-absolute assumptions do not leak into the Nextcloud build.
- **I5.** No user-supplied byte reaches the engine outside the documented
  `-iwad`/`-file`/`-deh` path.

## Error Behavior

| condition | behaviour |
|---|---|
| no IWAD selected or extracted | refuse with a visible message; do not start the engine |
| `prboomx.wad` missing from `index.data` | build error, not a runtime blank canvas |
| an imported file is not a WAD/DEH | reject on extension/type before writing to MemFS, and say which file |
| IDBFS unavailable (private browsing) | persist in memory and warn, as webdoom's `persist.js` does |
| remote download fails (if kept) | fall back to bundled Freedoom and a plain error, never a partial stack |
| GL selected on a build without GL | force software mode |

## Testing Strategy

- **Native regression:** configure/build the native tree in CI so the fork stays
  healthy (R8, I1).
- **Boot smoke test:** headless browser loads the app, selects Freedoom, reaches
  the title screen, no console errors.
- **WAD stack test:** import an IWAD plus two PWADs and a DEH; assert the engine
  argv and that the game starts on the expected map (the launch-arg assembly is
  the part most likely to regress).
- **Persistence test:** save, reload, confirm the save survives via IDBFS.
- **Nextcloud integration:** the subpath browser leg from the webdoom spec —
  correct wasm MIME, zero CSP violations, works under `/index.php/apps/...`.
- Dwasm's own `tests/` (`runtests.py`, `demo-testing.csv`) is demo-oriented and
  desktop-targeted; it is useful as a corpus, not as a CI gate.

## Phasing and effort

1. **Phase 1 — engine + wrapper.** Pin Dwasm, build wasm in CI, serve via PHP,
   bundle Freedoom, support `.wad` import, IDBFS saves. This is the shippable
   app.
2. **Phase 2 — content and parity with the hosted launcher.** Optional remote
   free-game downloads (with licence review), touch controls, URL args,
   user-facing settings; move the WAD/save library to Nextcloud files.
3. **Phase 3 — nothing engine-specific is planned.** MBF21/UDMF/DSDA demos are
   out (see Out of Scope); that path is the dsda port.

**Effort estimate (an assumption):** days to ~2 weeks of focused work for phase
1, because the browser port exists; the launcher and the packaging are the only
new code. This is the smallest of the three options.

## Out of Scope

- MBF21, UDMF, DSDA-format demos and dsda analysis. That is the dsda port.
- Netplay ("WebSockets support … has not yet been added" upstream; a WS proxy
  would be required, and Nextcloud has no in-process WebSocket).
- The OpenGL renderer as a default or requirement.
- Redistributing HACX, Harmony or REKKR without verified licences.
- A per-account WAD/save library (phase 2).
